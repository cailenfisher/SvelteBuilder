## What SvelteBuilder Is

SvelteBuilder is a production-ready SvelteKit scaffold and ecosystem designed for corporate software development. It targets full internationalization (i18n) and localization (l10n) from the ground up, with rock-solid accessibility and standards compliance baked in at every layer.

The ecosystem consists of:

- **`svelte-hermes`** — the i18n primitive library (LocalText, Locale, LocalTextLink, the `localText()` function, and the `<LocalText>` component)
- **`sveltebuilder-coreui`** — universal UI components shared across all domain modules
- **Domain module libraries** (e.g. `sveltebuilder-blog`, `sveltebuilder-logistic`, `sveltebuilder-commerce`) — production-ready feature sets for specific industries

This project was generated by the SvelteBuilder CLI and includes whatever modules were selected at creation time.

## The i18n Architecture — Read This First

Getting i18n right is the most important constraint in this codebase. The rules below are strict and non-negotiable.

### svelte-hermes is the single source of i18n primitives

Never redeclare or reimplement `Locale`, `LocalText`, `LocalTextLink`, the `<LocalText>` component, or the `localText(slug, scope?, entityId?)` function. Import them from `svelte-hermes` and only from there.

```ts
import { localText, type Locale, type LocalText, type LocalTextLink } from 'svelte-hermes';
```

### svelte-hermes never touches the database

The library is pure — it has no database access. The application (this project) owns locale resolution and dictionary loading. The app loads the dictionary and passes it to hermes via the `load` function, or supplies partial scoped layers via `merge`. svelte-hermes only reads what it is given.

### The app owns locale resolution and top-level UI text

Application-level labels — page titles, navigation items, button labels in layout chrome — are resolved by the app and passed down as plain `string` props. They do not go through hermes internally.

### Feature modules split into two tiers

Within any SvelteBuilder module (including coreui), components fall into one of two categories:

**UI/application components** — things like `Button`, `Modal`, `Tabs`, layout chrome:
- Receive plain `label: string` props and ordinary child snippets
- Do **not** import `svelte-hermes`
- Are i18n-agnostic by design

**Entity/domain components** — things like `ProductCard`, `TaskItem`, `InvoiceRow`:
- Receive the bare entity as props (the domain schema, no copy fields)
- Resolve their own user-facing copy by calling `localText(slug, scope, entityId)`
- **Do** import `svelte-hermes`

This split is intentional. `Button.svelte` and `ProductCard.svelte` in the same module will behave differently with respect to i18n, and that is correct.

### Domain schema carries no copy fields

Domain models (`Product`, `Task`, `EventSession`, etc.) do **not** have bare `name`, `title`, `label`, or `description` fields. User-facing copy is linked to the entity through `LocalTextLink` wiring, keyed by scope + entityId. The schema carries only `id`.

**Scope is implied, never a schema field.** By convention, scope matches the table/model name: the `Product` model resolves under the `product` scope. Do not add a `scope` column or prop. Only deviate with documented intent.

When modeling a new entity, never add a `title`/`name`/`label` field thinking to localize it later. The localized-content link is the model from the start — not an upgrade.

```ts
// Correct domain model
interface Product {
  id: string;
  sku: string;
  price: number;
  // No title, name, description — those live in the LocalText store
}

// Wrong — do not do this
interface Product {
  id: string;
  title: string;        // ❌ bare copy field
  description: string;  // ❌ bare copy field
}
```

## Naming Conventions

SvelteBuilder enforces holistic naming consistency: one name for one concept, unchanged from the database column to the TypeScript type to the Svelte component to the label the user reads. These are not style preferences — they are the connective tissue of the system.

### Quick Reference

| Layer | Convention | Example |
|---|---|---|
| SQL table | `singular_snake_case` | `user_account` |
| SQL column | `snake_case` | `email_address` |
| SQL primary key | always `id` | `id` |
| SQL foreign key | `<singular_table>_id` | `user_account_id` |
| SQL timestamp | `_at` suffix | `created_at` |
| REST path | `plural-kebab-case` | `/user-accounts` |
| JSON key | `camelCase` | `emailAddress` |
| TS variable/function | `camelCase` | `userAccount`, `loadUser` |
| TS type/interface/enum | `PascalCase`, singular, no prefix | `UserAccount`, `Locale` |
| TS enum value | `PascalCase` | `Status.Active` |
| TS constant | `SCREAMING_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| Svelte component file | `PascalCase.svelte` | `UserCard.svelte` |
| Svelte route folder | `kebab-case` | `user-account/` |
| Non-component module | `kebab-case.ts` | `format-date.ts` |
| CSS class | `kebab-case` BEM | `card__title--active` |
| CSS custom property | `--kebab-case` | `--color-primary` |
| HTML attribute | `kebab-case` | `data-user-id` |

### Key Rules

**Singular everywhere except REST paths.** Tables, types, component names, route segments — all singular. REST collection endpoints are the one deliberate exception (`GET /user-accounts`).

**No abbreviations.** Spell words out. Autocomplete makes length free; ambiguity is expensive. The only sanctioned exception is `id` (universally understood). Acronyms (`http`, `url`, `api`) are acceptable; abbreviations (`usrCfg`, `calcRegTot`) are not.

**No `is_` / `has_` boolean prefixes.** Name the state: `active`, not `isActive`. `emailVerified`, not `hasVerifiedEmail`. This applies to SQL columns, TypeScript fields, and Svelte props alike.

**No `I` prefix on interfaces, no `T` prefix on type aliases.** Types are named for their concept: `UserAccount`, `Locale` — not `IUserAccount` or `TLocale`.

**Acronyms are ordinary words.** Capitalize only the first letter in context: `getHttpUrl()`, `HtmlParser`, `apiKey` — not `getHTTPURL()` or `HTMLParser`.

**One concept, one name.** Before introducing a new noun, check whether the concept already has a name. The `user_account` table maps to the `UserAccount` type, the `UserCard.svelte` component, the `/user-accounts` endpoint, and the `userAccount` variable. Nothing in that chain diverges.

## Architecture Rules

### Where things live

```
src/
  lib/
    components/     # Reusable Svelte components (PascalCase.svelte)
    server/         # Server-only modules (never imported client-side)
    types/          # TypeScript type definitions
    utils/          # Utility functions (kebab-case.ts)
  routes/
    [resource]/     # Route folders in kebab-case, singular segments
      +page.svelte
      +page.server.ts
```

### Data flow

1. `+page.server.ts` (or `+layout.server.ts`) loads data from the database, resolves the active locale, and loads the hermes dictionary
2. The page/layout calls hermes `load()` or `merge()` with the dictionary payload
3. Entity components call `localText(slug, scope, entityId)` to resolve their own copy
4. Application UI components receive plain string props — they never call `localText` directly

### coreui components first

Before building a new UI component, check `sveltebuilder-coreui`. If a suitable component exists, use it. If you need a variation, extend or compose it rather than duplicating. If a new component would be useful across multiple domain modules, propose it as a coreui addition.

### No database access in components

Components never import database clients or query directly. All database interaction happens in `+page.server.ts`, `+layout.server.ts`, or dedicated server-side modules in `src/lib/server/`.

### Schema-first modeling

When creating a new entity, define the database schema and TypeScript type before building components. The type drives everything else. Remember: no copy fields in the type.

## Accessibility and Standards

SvelteBuilder targets WCAG 2.1 AA compliance as the baseline. When generating components:

- Use semantic HTML elements (`<nav>`, `<main>`, `<article>`, `<section>`, `<button>`, etc.) rather than generic `<div>`/`<span>` wherever semantics apply
- Include appropriate ARIA attributes when semantic HTML alone is insufficient — but prefer semantic HTML over ARIA
- All interactive elements must be keyboard-operable and have visible focus indicators
- Images require descriptive `alt` text; decorative images use `alt=""`
- Color alone must never be the sole means of conveying information
- Test with keyboard navigation in mind when reviewing generated component code

## Common Prompting Patterns

Use these as starting points when prompting Claude Code in this project.

### Adding a new domain entity

```
Add a new `[EntityName]` entity to [module].
- SQL: singular snake_case table, no copy columns, id as UUID primary key
- TypeScript: PascalCase interface, no title/name/label fields
- Scope for localText resolution: [scope name, usually matches table name]
- Components: one for the entity card/row (calls localText), one list wrapper
```

### Adding a new route

```
Add a route for [resource] at /[kebab-case-path].
- +page.server.ts loads data and calls hermes load/merge for the locale
- +page.svelte uses <LocalText> or localText() for entity copy
- Application chrome labels are plain strings passed as props from the layout
```

### Adding a UI component to coreui

```
Add a [ComponentName] component to sveltebuilder-coreui.
- It is a UI/application component: accepts plain string props, no svelte-hermes import
- Props follow no-is/has prefix rule for booleans
- Use semantic HTML, WCAG 2.1 AA compliant
- Expose a default snippet for content composition where appropriate
```

### Adding a localized entity component

```
Add a [ComponentName] component for the [entity] entity in [module].
- It is a domain component: imports localText from svelte-hermes
- Props: the bare entity schema (id + domain fields, no copy fields)
- Resolves copy via localText(slug, '[scope]', entity.id)
- Uses coreui components for its UI structure
```

### Extending the dictionary

```
Add LocalText entries for [entity/feature].
- Scope: [scope]
- Slugs needed: [list of slugs]
- Do not add copy fields to the entity schema
- Wire via LocalTextLink in the existing content store
```

## What Not to Do — Checklist

When reviewing generated code, flag and fix any of these:

- [ ] `title`, `name`, `label`, or `description` added to a domain schema
- [ ] `svelte-hermes` imported in a UI/application component (Button, Modal, etc.)
- [ ] `localText` called in a `+page.svelte` for entity copy instead of in the entity component
- [ ] Database access inside a `.svelte` file
- [ ] `Locale`, `LocalText`, or `LocalTextLink` redeclared rather than imported from `svelte-hermes`
- [ ] `isActive`, `hasPermission`, `isOpen` boolean naming
- [ ] `IUserAccount`, `TLocale` type prefixes
- [ ] Abbreviated names: `usrCfg`, `calcTotal`, `evtSess`
- [ ] Copy fields in domain schema intended to be "localized later"
- [ ] `scope` as a schema field or prop (it is implied by convention)
- [ ] Non-semantic `<div>` used where `<button>`, `<nav>`, `<article>` etc. would apply
- [ ] New UI component built from scratch when a coreui equivalent exists
