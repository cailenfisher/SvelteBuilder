# Auth, the Principal–Identity Split, and RLS Access Patterns

> **Status:** Draft — awaiting human review before publication to the GitHub wiki.

---

## The two-layer model

SvelteBuilder separates **auth identity** from **domain principal**. These are distinct concepts that live in separate database schemas and are never mixed.

| Layer | Location | Type | Purpose |
| ----- | --------- | ---- | ------- |
| Auth identity | `auth.user` | Text PK | Managed by the auth provider (Auth.js or Supabase). Holds email, name, image. Provider creates this row on first sign-in. |
| Domain principal | `public.user_account` | Bigint PK | Owned by the application. Referenced by all domain tables, RLS policies, and `local_text_link.entity_id`. |

The link between them is `user_account.auth_user_id text`, which stores the provider's user ID as a text value. The provider's type choice (Auth.js uses text, Supabase uses UUID stored as text) is accepted inside `auth.*` and never propagates into `public.*`.

### Why the separation matters

- `user_account.id` is a `bigint` generated by Postgres sequences. This is required because `local_text_link.entity_id` is a single polymorphic `bigint` column that must hold IDs from any domain table. UUID PKs are incompatible with this design.
- The auth provider's schema uses its own conventions (camelCase columns in Auth.js, Supabase's own column names). These are accepted inside `auth.*` and never leak into `public.*`.
- Replacing the auth provider (e.g., moving from Supabase to Auth.js) only changes `auth.*` and the single `resolveAuthenticatedUserId` function. No domain table schemas or RLS policies change.

## The session variable convention

RLS policies identify the current user through a Postgres session variable:

```sql
create or replace function public.current_user_id()
returns bigint
language sql
stable
as $$
  select nullif(current_setting('app.current_user_id', true), '')::bigint;
$$;
```

**The `STABLE` marking is non-negotiable.** Postgres evaluates `STABLE` functions once per transaction rather than once per row. Without it, every row scanned by a policy re-executes the function, making RLS expensive on large result sets. `VOLATILE` (the implicit default) is wrong here.

The variable is set inside the `withUser` wrapper in TypeScript before any query runs in the transaction:

```ts
await tx.execute(sql`
  select set_config('app.current_user_id', ${String(userAccountId)}, true)
`);
```

The third argument `true` makes the setting transaction-local — it is automatically cleared when the transaction ends.

## The `withUser` database access pattern

All database calls in route code (load functions, form actions, API handlers) go through:

```ts
const result = await event.locals.db.withUser(async (tx) => {
  return tx.select(...).from(table).where(...);
});
```

The wrapper is injected by `hooks.server.ts` via `createUserScopedDb(userAccountId)`. It is the only path for route code to reach the database. The raw Drizzle `db` instance is intentionally not accessible from route imports.

### Grouping decisions

- Group queries that are **logically atomic** into a single `withUser` call. If two queries must both succeed or both fail, they belong in the same transaction.
- Keep **independent queries in separate** `withUser` calls. Do not combine unrelated reads into one transaction for the sake of reducing call count.
- **Never include external work inside `withUser`.** HTTP requests to third-party APIs, file system reads, queue enqueues — these must happen outside the transaction boundary. If a handler needs DB → external API → DB, that is two separate `withUser` calls with the external work between them.

### Deliberate exceptions to the `withUser` rule

Three locations import the raw `db` directly, by design:

| Location | Reason |
| -------- | ------ |
| `src/lib/server/auth-resolver.ts` | Bootstrap lookup — resolves the provider user ID to `user_account.id` before user context exists. Cannot use `withUser` because the user ID is what `withUser` needs. |
| `src/hooks.server.ts` (locale query) | The locale table is world-readable (`locale_public_read: using (true)`). No RLS context required. |
| Migration scripts and seed runners | No request context exists. These use the raw client with whatever Postgres role they connect as. |

Each exception is documented with a comment in the source file.

## RLS policy patterns

### Owner-read / owner-update

```sql
create policy "user_account_owner_read"
  on public.user_account for select
  to authenticated
  using (public.current_user_id() = id);
```

`current_user_id()` is `STABLE`, so Postgres evaluates it once per transaction and reuses the result for every row. The comparison target is the `bigint` PK, not a UUID.

### Admin all-access

```sql
create policy "navigation_item_admin_write"
  on public.navigation_item for all
  to authenticated
  using (
    exists (
      select 1 from public.user_account
      where id = public.current_user_id() and admin
    )
  )
  with check (
    exists (
      select 1 from public.user_account
      where id = public.current_user_id() and admin
    )
  );
```

Admin access is gated on `user_account.admin boolean`. The subquery is cheap: `current_user_id()` is `STABLE` (evaluated once per transaction), and the lookup uses the `user_account` primary key.

**No JWT claims are used.** The old `auth.jwt() ->> 'role' = 'admin'` pattern is removed entirely. Promoting a user to admin means setting `admin = true` in `user_account`.

### Author-scoped with owner comparison

```sql
create policy "post_author_all"
  on public.post for all
  to authenticated
  using (user_account_id = public.current_user_id())
  with check (user_account_id = public.current_user_id());
```

`user_account_id` is `bigint` — the same type returned by `current_user_id()`. The old pattern used `auth.uid()` (a UUID) compared to a UUID column; that comparison target is now the domain principal's `bigint` PK.

## The template seam

Both SvelteBuilder scaffold templates (`superprototype` and `native`) share an identical `hooks.server.ts`. The only difference between them is the implementation of `resolveAuthenticatedUserId` in `src/lib/server/auth-resolver.ts`:

```ts
// Shared signature — same in both templates
export async function resolveAuthenticatedUserId(
  event: RequestEvent,
): Promise<bigint | null>
```

**SuperPrototype implementation:**
1. Calls `event.locals.supabase.auth.getUser()` to verify the Supabase session.
2. Queries `user_account` where `auth_user_id = user.id` (Supabase UUID as text).
3. Returns `user_account.id bigint`.

**Native implementation:**
1. Calls `event.locals.auth()` to get the Auth.js session.
2. Queries `user_account` where `auth_user_id = session.user.id` (Auth.js text ID).
3. Returns `user_account.id bigint`.

The shared hook:

```ts
const populateLocals: Handle = async ({ event, resolve }) => {
  const userAccountId = await resolveAuthenticatedUserId(event);
  event.locals.userAccountId = userAccountId;
  event.locals.db = createUserScopedDb(userAccountId);
  return resolve(event);
};

export const handle = sequence(providerHandle, populateLocals, localeHook);
```

`providerHandle` is also template-specific (re-exported from `auth-handle.ts`). Everything else in `hooks.server.ts` is identical.

## Auth.js user provisioning (Native only)

When Auth.js creates a new row in `auth.user`, the `events.createUser` callback provisions `public.user_account`:

```ts
events: {
  createUser: async ({ user }) => {
    if (!user.id) return;
    const existing = await db
      .select({ id: userAccount.id })
      .from(userAccount)
      .where(eq(userAccount.authUserId, user.id))
      .limit(1);
    if (existing.length === 0) {
      await db.insert(userAccount).values({ authUserId: user.id });
    }
  },
},
```

This is idempotent. The provisioned `user_account` starts with `active = true` and `admin = false`. To grant admin access, set `admin = true` directly in the database.

## Environment variables

### SuperPrototype

| Variable | Purpose |
| -------- | ------- |
| `DATABASE_URL` | Direct Postgres connection string for Drizzle |
| `PUBLIC_SUPABASE_URL` | Supabase project URL (for Auth SSR client) |
| `PUBLIC_SUPABASE_ANON_KEY` | Supabase anon key (for Auth SSR client) |
| `SUPABASE_SECRET_KEY` | Supabase service role key (server-only) |

### Native

| Variable | Purpose |
| -------- | ------- |

| `AUTH_MICROSOFT_ENTRA_ID_ID` | Microsoft Entra (Azure AD) app client ID |
| `AUTH_MICROSOFT_ENTRA_ID_SECRET` | Microsoft Entra client secret |
| `AUTH_MICROSOFT_ENTRA_ID_ISSUER` | Tenant issuer URL: `https://login.microsoftonline.com/{tenant}/v2.0` |
| `AUTH_GOOGLE_ID` | Google OAuth client ID |
| `AUTH_GOOGLE_SECRET` | Google OAuth client secret |
| `AUTH_GITHUB_ID` | GitHub OAuth App client ID |
| `AUTH_GITHUB_SECRET` | GitHub OAuth App client secret |

Set `AUTH_TRUST_HOST=true` when deploying behind a trusted reverse proxy (Vercel, Cloudflare, Fly.io).

## Migration note: SuperPrototype RLS and Postgres roles

The `withUser` pattern calls `set_config('app.current_user_id', ...)` inside each transaction, and `current_user_id()` reads it back for RLS. For this to **enforce** RLS, the Postgres connection must use a non-superuser role that is subject to row-level security.

When connecting directly to Supabase with the `postgres` superuser (the default `DATABASE_URL` format), the superuser bypasses RLS. Production deployments should use a restricted Postgres role — either the Supabase `authenticated` role (set via `SET ROLE authenticated`) or a custom application role — with appropriate grants on all tables.

This is a known deployment consideration. The RLS policies and `current_user_id()` function are correct; enforcing them requires the right connection role.
